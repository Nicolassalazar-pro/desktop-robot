## Security [SEC]
> Last reviewed: 2026-08-07 | Open: 2

Scope: ESP32-S3 firmware serving its own WPA2 softAP (`Hanger OVERRIDE` / `TheGarageAtl`, fixed by design per PROJECT-HISTORY.md D6; rotation explicitly rejected R8, R23, R28). Threat model = unauthorised physical actuation by anyone in WiFi range, not data exfiltration. The physical-presence trust model is: LCD screen visibility ⇒ authorised to drive. Only new findings are listed; the "fixed WPA2" itself is out of scope per the review brief.

What was verified sound (evidence in `src/main.cpp`):

- **Access token generation.** 64-bit per-activation token, two `esp_random()` uint32s formatted as 16-hex-char (`generateActivationCredentials` at 5345–5366). Invalidated (`secureZero`) on every teardown path (`enterIdleDemo`, `stopWifiServer`, activation-terminal-fault).
- **Access token validation.** `requestHasValidAccessToken` (5408–5441) enforces exactly one `k=` query param (rejects duplicates at 5423), length-checks before compare, then uses a constant-time XOR-OR loop over the full expected length. Not URL-decoded a second time, not case-folded — matches the QR-embedded canonical form only.
- **WS auth is enforced at HTTP handshake.** `WsAuthGuardHandler` (1595–1610) is registered BEFORE `g_orWs` (9866–9867). An unauthenticated `/ws` upgrade is answered with a plain 403 and no `AsyncWebSocketClient` is ever constructed (this closed the prior `close()`-from-inside-`WS_EVT_CONNECT` use-after-free at 9852–9865). A defence-in-depth re-check at `WS_EVT_CONNECT` (8675) covers race-conditional acceptance.
- **HTTP root also gated.** `/` requires the same token (9871); catch-all `onNotFound` (9888) returns a bare 404 with no auth-scoped content.
- **Transport ownership is exclusive.** Second-comer WS clients hit 8714–8737 and are `close(1008, "Owner busy")`d before ever being accepted as owner. Non-owner data frames trigger `client->close()` at 8830–8837. DriveSession double-enforces owner identity by pointer (`hasOwner_ && owner_ == client`).
- **Binary opcode parsers refuse malformed input.** Every case in the switch at 8865–8969 validates exact frame length (`kOpControl=4`, `kOpTrim=6`, `kOpMood/Gesture/Sound=3`); anything else → `MalformedControl` → `terminateWsTransportForProtocolFault` → activation-wide terminal fault (poisons remainder of activation, not just this transport). Unknown opcodes fall through the same fault path.
- **ID indexing is bounds-checked.** `isValidMoodId` (8519–8522), `patternNameAt` (movement_expression.cpp:305–306), and sound opcode's explicit `switch 0/1/2/default` (9280–9288) all reject out-of-range IDs before use as table indices. `int8_t` casts of control bytes are further range-checked to `[-100, 100]` in `DriveSession::commandIsValid` (drive_session.cpp:315–317).
- **Memory safety.** The only wire-fed `memcpy` (8885) copies exactly `sizeof(event.values)` = 4 bytes and is preceded by `len == 6U` gate. All `snprintf` sites (31 occurrences) pass `sizeof(buf)`. No `strcpy`/`sprintf`/`gets`. `SerialLineBuffer` (serial_line_buffer.h) is bounded, printable-only, and enters a discard-until-CRLF state on overflow — no line-length overflow reachable from serial.
- **LCD gesture-menu buttons are inert to physical touch.** `gestureButtonAt` (1517–1525) returns `-1` for the three mood buttons; only the `testSlot` button responds and only when `testSlotArmed()`. So the "someone leans on the touchscreen" attack for remote-triggerable gestures (frustrated/excited/scared) does not exist — an attacker at the screen still needs bench-arming, which requires prior serial (USB) access to set.
- **Safety interlocks fire independently.** 300 ms software lease inside `DriveSession::tick`, plus an independent hardware esp_timer that calls `handleDriveHardwareTrip` (8990) → `resetDriveControl`. WS queue overflow → `handleWsQueueEmergency` (8977) → `resetDriveControl`. `resetDriveControl` (5832) drains ingress via `beginWsIngressQuarantine`, powers down motors, then re-enables ingress. Quarantine drain is bounded (`kIngressDrainTimeoutMs`, 5807–5815) so a stuck AsyncTCP callback cannot cause a watchdog reset while the drive rail is on.
- **Serial actuation is out of remote scope.** `gesture`, `spin`, `straight`, `turn`, `cal erase confirm` (3161–3183) all require physical USB-CDC access via GPIO19/20 on the exposed pins (HARDWARE.md §1). No remote path (WS, HTTP, WiFi frames) can inject a line into the serial console.

Attacker in WiFi range **without** AP password: nothing — WPA2 802.11i blocks all IP-layer access, and the 4-slot cap does not accept them.

Attacker **with** AP password (i.e., has photographed the WIFI QR / cracked WPA2) but **without** the URL token: cannot move the robot. Every HTTP and WS route rejects at 403; brute-forcing the 64-bit token over TCP is infeasible on ESP32-S3 (upper-bound of a few tens of connect attempts per second against a per-activation random). Can, however, connect to the softAP and consume client slots — see SEC-1.

Attacker with **both** the AP password and the URL token (has seen the LCD screen): can drive the robot. This is the intended trust boundary per D6/D18 (screen-visibility = authorisation).

Highest-risk finding: **SEC-1** (physical DoS via AP client-slot exhaustion — a WPA2-authenticated attacker can prevent the operator from associating, forcing a reboot).

### SEC-1 — Password-holder can lock the legitimate operator off the softAP
- Severity: MEDIUM
- Status: OPEN
- File: `src/main.cpp:5228, 9962-9964`
- Problem: The AP is provisioned with `max_connection = kOverrideApMaxClients = 4`. Any device that knows the fixed WPA2 password can associate up to four times (four MACs, or one MAC in four contexts) and hold the association open, blocking any further station — including the legitimate operator's phone — from joining. The associated device does not need the URL activation token to hold the slot; association happens at 802.11 layer, before HTTP/WS auth ever runs.
- Why: Because the WPA2 password is fixed by design (D6) and printed on the LCD as a QR code, the population who *can* associate is unbounded over the lifetime of the device — anyone who has ever been in line-of-sight of the screen retains this capability. Denying the operator association is not itself an actuation exploit, but it prevents the intended "operator scans QR, connects, drives" flow, forces a physical power-cycle to recover (there is no watchdog on softAP client activity), and — critically — prevents the operator from sending a manual STOP if a legitimate session ends unexpectedly with the motors already commanded (the 300 ms lease will still cut power, so the outcome is "robot stops and cannot be resumed remotely", not "robot runs away", but it is still a physical control-loss primitive available to anyone in RF range without needing the URL token). This is *not* the "hardcoded WPA2" complaint that R8/R28 rejected — it is the specific consequence of that decision *combined with* `max_connection=4` and no per-station eviction.
- Fix: Do not touch the credential model (D6 is respected). Either (a) raise `kOverrideApMaxClients` toward the 10-station ESP32 softAP cap so slot exhaustion requires substantially more effort — cheap and gives the legitimate operator statistical headroom — or (b) implement an idle-station timeout: use `esp_wifi_ap_get_sta_list` on a slow tick and `esp_wifi_deauth_sta(aid)` on stations that have neither completed a captive-portal fetch of `/` nor opened `/ws` within, say, 10 s of associating. Option (b) is the real fix; option (a) is the one-line placeholder. Do not add HTTP rate-limiting — the attacker never gets to HTTP.

### SEC-2 — Sequence-freshness window is 127 forward, which is wider than the ownership model needs
- Severity: LOW
- Status: OPEN
- File: `src/drive_session.cpp:302-308`
- Problem: `DriveSession::sequenceIsFresh` accepts any delta in `[1, 127]` on the 8-bit sequence. That is half of the sequence space in one direction. It is not exploitable today because only the transport owner (holder of the URL token) can push data frames — non-owner frames are `close()`d at `main.cpp:8830-8837` before they ever reach `DriveSession::frame`. But the width of the acceptance window is doing no useful work: a legitimate operator's frames arrive over a single ordered WS/TCP flow, so a delta of `1` (or at most a small window) suffices in the good case.
- Why: A 127-wide window means that if any future change ever weakens the ownership check — e.g., a spare non-owner client that is allowed to send "diagnostic" frames, or a state where the owner slot is briefly cleared between transports without a matching sequence reset — an in-range attacker can inject a control frame with `seq = lastSeq + 64` and be accepted. The current design has no such gap, so this is a latent-brittleness finding, not a live vulnerability. Filing at LOW because the fix is a two-line change that makes the audit story simpler: the tighter the window, the smaller the "if ownership breaks, what else has to break for this to bite" chain.
- Fix: Tighten the acceptance window to something that matches the physical send cadence (drive frames are sent at ~30 Hz over a 300 ms lease → at most ~10 frames in flight worst case). Replace the check with `delta >= 1 && delta <= 16`. Reject anything else and log at the same telemetry channel that already reports fault reasons, so a bug in the sender surfaces as a visible fault rather than a silent drop.
